# 子系统 subagent 提示词模板

编排器把本文件全文发给 subagent，并在末尾附上四段材料：`subsystem`（id 与名称）、`excerpt`（该子系统的题面原文）、`contract`（全题命令、错误码、观察通道的短列表）、`profile` 与 `work_order`（首轮为空）。不要把摘录改写成测试规格说明书或 testspec。

被测对象按无界面的接口和逻辑处理。不修改 `testaw.py`、`udpunittest.py`、`.ctb/design.json`。那些文件只由编排器写入。

## 返回

只返回一个 JSON 对象，不要附分析报告：

```json
{
  "subsystem_id": "S01",
  "mechanisms": [],
  "hypotheses": [],
  "case_sketches": [],
  "gaps": []
}
```

`mechanisms`、`hypotheses` 与 `references/design-playbook.md` §3、§4 的字段相同。每条假设包含 `target`、`operator`、`priority`、`fault`、`reach`、`infect`、`propagate`、`basis`。`basis` 只用 `public_spec` 或 `reference_observed`。

`case_sketches` 每条只含：`id`、`title`、`pre`、`steps`、`expect`、`method`、`hypotheses`、`priority`。`method` 取下面八种之一。一条草稿只钉住一个判定点。`steps` 写成可落到 AW 调用的动作和参数，不写界面操作。

题面没有给出的阈值、公式、错误码放进 `gaps`，不编成用例。

## 做法

1. **抽规则。** 从摘录列出输入、守卫、状态写、错误码、公式、状态和它们的读写。每个响应码对应一个守卫。失败路径写明哪些状态必须保持。
2. **故障假设。** 沿用手册主线：机制元素 → 故障算子 → 可达（reach）→ 激发（infect）→ 传播（propagate）。算子用手册 §4 的名称。核心效果、每个守卫的 `G-DROP`/`G-BND`、拒绝后仍写入的 `E-FAIL` 标 P0。`profile` 的广度按 e2e-test 技能中的 Profile 表执行，不降低断言要求。
3. **选区分值。** 用下面的手法为假设选数据，并在 `method` 里标明主手法。先做手册 §5.1 的两错检验：数据要让常见错误实现和正确实现的输出不同。
4. **增量轮。** `work_order` 非空时，优先补本子系统里仍是 MISS 或模型缺口的机制，已命中用例不改意图。拿不出新假设时 `hypotheses` 为空，并在 `gaps` 写 `no_new_hypothesis`。

## 无界面逻辑手法

| 手法 | 怎么用在接口上 | 常对应的算子 |
| --- | --- | --- |
| 等价类 | 每种不同处理留一个有效类；每个无效类单独一条，只违反一个守卫 | `G-DROP`、`O-CODE` |
| 边界值 | 有效边界及其两侧：阈值、阈值−1、上限、上限+1；累计后再取边界 | `G-BND`、`E-ACCUM` |
| 非法输入 | 缺参、类型错误、空、负数、未知 id、枚举之外的值。预期为错误码，且状态不变 | `G-DROP`、`O-CODE`、`E-FAIL` |
| 状态迁移 | 每个合法迁移一条；每个禁止迁移一条；迁移后立刻做下一步，确认没有停在中间态 | `S-TRANS` |
| 判定表 | 多条件共同决定结果时：全部满足一条，每个条件单独为假各一条。失败不产生部分写入 | `G-LOGIC` |
| 数值取整 / 溢出 | 按题面公式手算。覆盖 0、刚好整数、差一个最小单位、上限、上限之上。写明取整方向 | `E-CALC` |
| 守恒不变量 | 成功时减少量等于规则消耗、增加量等于规则产出。失败时相关变量与调用前相同。结果不为负，不超过上限 | `E-MISS`、`E-FAIL`、`E-CALC` |
| 重复执行 / 幂等 | 同一命令或同一业务标识再提交一次。计数、资源、归属、积分只变化一次 | `E-ACCUM`、`L-STALE` |
| 异常与错误码 | 每种错误码一条，断言完整响应，不只看前缀。拒绝后再做一次合法操作，确认状态仍是拒绝前的值 | `O-CODE`、`E-FAIL` |

观察至少到手册 §5.2 的要求：效果类看到状态或后续操作，拒绝类看到完整错误码和状态保持。

## 游戏类多子系统题型：易错点参考

本节只供「无界面、多子系统、数据从一个模块流到下一个模块」的题型参考。建设、组军、争夺、结算是这类题的例子，不是某道固定题目。题面没有的环节不要设计，把缺口写入 `gaps`。子任务只处理自己的摘录；上游产物写成前置中的具体数字，不展开其他子系统内部。

数据流例子：建设产出资源 → 组军消耗资源并形成编制 → 争夺用这支军队改变领地归属 → 结算按争夺结果计分。

| 示例环节 | 优先假设的错误 |
| --- | --- |
| 建设 | 升级条件漏掉其中一个仍成功；资源不足仍扣减或扣成负数；等级已达上限仍能再升；产出取整方向错；失败的升级仍写入等级 |
| 组军 | 兵种配比差 1 仍通过；人口或编制等于上限被拒绝、上限+1 却通过；资源不足时仍然占用人口或留下半支军队；重复组建扣两次资源 |
| 争夺 | 攻防相等的平局归属写错；取整后才相等的情况被当成胜；兵力 0 仍发生归属变更；两支军队同时争夺时两边都成为归属方；战损大于出征数 |
| 结算 | 公式项漏乘或取整时机错；0 分、刚好上榜、差 1 分的名次错；并列时下一名次跳号或连续与题面不符；同一结果重复结算再次加分；失败或平局按胜利加分 |

跨子系统的传递、差 1 点拒绝、重复结算只生效一次，由编排器写联动用例。子任务发现摘录里的输出会被下游读取时，在假设的 `propagate` 里写明要观察的输出字段即可。
